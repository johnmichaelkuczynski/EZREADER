What's different about this app — Classic EZ Reader's defining features
Classic EZ Reader is a Flask + Jinja2 + vanilla-JS single-page text-processing platform with six LLM providers, SSE streaming for every long-running operation, a Cross-Chunk Coherence (CC) reconstruction engine backed by Neon Postgres, and two hard product invariants (no dollar signs, max 4 sentences per paragraph). Seven things make it different from previous R1 targets:

Single-page Jinja2 template, not SPA. templates/index_clean.html is ~4740 lines of inline HTML + CSS + vanilla JS. There's no React, no testid convention, no shadcn. R1 must use semantic selectors (DOM IDs like #inputText, #outputText, #humanizerOutput) — the blueprint enumerates these in Part 7 as canonical.
Mode buttons require DOUBLE-CLICK. Per blueprint Part 11 UI convention #6: "Mode buttons require DOUBLE-CLICK to activate (legacy quirk). Single-click only selects." R1 must use .dblclick() for mode-selecting buttons, OR use the floating ACTION buttons (green in input, red in output) which bypass the double-click requirement. R1 must verify this convention holds and isn't accidentally broken.
TWO hard product invariants enforced post-LLM. The $ symbol is stripped at input via preprocess_dollar_signs() AND from every output. force_paragraph_formatting() forcibly splits any paragraph >4 sentences AFTER the LLM responds. Both are non-negotiable. R1 verifies both by deliberately submitting inputs that would violate them and confirming the output complies.
The CC engine has STRICT failure semantics and pacing expectations. Per blueprint Part 2 Feature 2: ~20 seconds per chunk, "finishing in under 10 minutes for a long doc means something was skipped." Any chunk failing permanently → job marked failed (not silently completed). R1 verifies the pacing AND the strict failure semantics.
Dual-database pattern in same Neon instance. SQLAlchemy tables (user, text_entry, chat_message, etc.) AND raw psycopg2 tables (reconstruction_jobs, reconstruction_chunks). R1 doesn't connect to Postgres directly but verifies state via the GET /reconstruction/status/:id and GET /reconstruction/result/:id endpoints.
Six LLM providers with key rotation. OpenAI, Anthropic, DeepSeek, Perplexity, Venice (May 2026), Azure. Each has multi-key support (OPENAI_API_KEY_2, _3, etc.). Failover order is fixed. R1 verifies provider switching works AND that POST /reset_api_keys resets health flags.
GPTZero "X% HUMAN" displayed on every text-producing box and updated after every transformation. R1 verifies this updates correctly across all four boxes (input, output, humanizer style, humanizer output).

The ten invariants that elevate to CRITICAL VIOLATION status:
Invariant A — No dollar signs anywhere in input or output. Per blueprint Part 11 #1, this is a hard product requirement. R1 deliberately submits input containing $5.99, costs $200, the price is $99. After ANY transformation (rewrite, humanize, translate, assess, CC reconstruction), R1 scans the output for $ characters. Any $ in output text = CRITICAL VIOLATION. Also: R1 scans output for currency words that should have replaced dollar signs — if a dollar amount appears unstripped as the literal sequence "$NNN" anywhere in the output box, the strip is broken.
Invariant B — 4-sentence-per-paragraph maximum. Per blueprint Part 11 #2, force_paragraph_formatting() enforces this absolutely. R1 submits input containing a paragraph of 8+ sentences (no paragraph breaks). After any rewrite operation, R1 splits the output by double-newline into paragraphs, then splits each paragraph by sentence-terminator (. , ! , ? ). Any paragraph containing more than 4 sentences = CRITICAL VIOLATION. R1 allows ±1 leniency for edge cases (e.g., abbreviations counted as sentence breaks), so threshold is 6+ sentences per paragraph triggers violation.
Invariant C — CC three-pass SSE event sequence. When R1 submits POST /reconstruction/start_stream, the SSE event stream MUST contain (in order): init → job_created → skeleton_start → skeleton_done → chunks_start → chunk_processing+chunk_complete (per chunk) → stitch_start → stitch_done → output (with text) → complete. If any of these documented event types is missing on a successful job, or if they fire out of order (e.g., chunk events before skeleton_done), CRITICAL VIOLATION.
Invariant D — CC pacing is enforced. Per blueprint Part 2 Feature 2, 2-3 second inter-chunk pauses are protective and intentional. R1 measures elapsed time per chunk during a CC run. If average time-per-chunk is < 8 seconds across all chunks, CC has skipped the protective pauses: CRITICAL VIOLATION ("under 10 minutes for a long doc means something was skipped"). R1 sizes the input so the CC run has at least 5 chunks to give a meaningful average.
Invariant E — CC strict failure semantics. R1 verifies the failure-marking behavior by running a CC job and inspecting GET /reconstruction/status/:id mid-run and post-run. If status ever shows complete while any chunk in reconstruction_chunks has status failed, that's a silent-success violation. The blueprint is explicit: any permanent chunk failure must mark the WHOLE job as failed. R1 cannot easily force a chunk failure, but R1 can verify the schema correctness: status field values observed must be in {pending, skeleton_extraction, chunk_processing, stitching, complete, failed} — any other value indicates a broken state machine. R1 also verifies via the SSE stream that error events terminate the job if they appear.
Invariant F — CC owner-only access enforcement. Per blueprint Part 12 #3, the owner check uses session.user_id || session._user_id || 'anonymous'. R1 creates a CC job while logged in as user A, captures the job_id. R1 then opens a fresh Playwright context (no session cookie), and attempts GET /reconstruction/status/:job_id and GET /reconstruction/result/:job_id. Both must return 404 (per blueprint) or 401/403. If either returns the actual data, CRITICAL VIOLATION (cross-user data leak on a primary content endpoint).
Invariant G — Provider routing actually works. R1 submits the same input through all 6 providers (anthropic, openai, deepseek, perplexity, venice, azure — skipping any whose API key is missing per app boot logs). Each response captured. No two outputs byte-identical (would indicate silent fallback). If any pair byte-identical, CRITICAL VIOLATION.
Invariant H — Key rotation reset works. R1 calls POST /reset_api_keys. R1 then verifies (via a subsequent successful provider call) that the reset didn't break anything. Per blueprint, this manually clears failure_count and rate_limited_until flags. If POST /reset_api_keys returns success but subsequent provider calls fail with "all keys exhausted," reset is broken: CRITICAL VIOLATION. R1 cannot easily verify health-flag clearing without internal state access; the test is just that reset doesn't break the next call.
Invariant I — AI detection updates on all four boxes. After a humanizer round-trip, R1 captures the GPTZero score displayed on (a) input box, (b) output box, (c) humanizer style input box, (d) humanizer output box. After the round-trip completes, all four should show a numeric percentage (not "—" or empty). If any box still shows placeholder/empty score 10 seconds after rewrite completion, CRITICAL VIOLATION (the documented behavior in blueprint Feature 10 is broken).
Invariant J — File upload routing. Per blueprint Feature 8 + October 2025 fix, Content Source and Critique uploads must hit /api/content_source/upload and /extract_text respectively. R1 uploads a PDF to each box and verifies the correct route fires (route-specific check, not boolean). If Content Source upload hits the wrong route (e.g., /upload or /extract_text instead of /api/content_source/upload), the documented October 2025 fix has regressed: CRITICAL VIOLATION.
Architecture

Browser automation: Playwright (Node, single-file tools/r1/run.mjs). Standalone Node project, not in any workspace.
R1's brain: Anthropic API. Model: claude-opus-4-7. Key in ANTHROPIC_API_KEY.
Judge: Separate Claude API call per interaction. Prose critique. For rewrite/humanize quality, judge gets input + output and assesses whether transformation was substantive AND whether the dollar-sign + paragraph invariants hold.
Live view: node:http server on port 7777. Zero extra deps.
Target app: Classic EZ Reader running locally. Default APP_URL=http://localhost:5000. R1 registers/logs in via Flask-Login session.
